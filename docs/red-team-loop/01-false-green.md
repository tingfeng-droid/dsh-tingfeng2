# 假干净：仪器和产品一起瞎

> 系列之一｜素材：2026-11-21~22，dsh-tingfeng2 插件反方复验，第 10–14 轮

11 月 22 日深夜，一个会话检索插件的第十四轮收口。修复方自报"全套绿灯"：回归 181 条 0 失败、审计 0 泄漏、闭包双 CLOSED。两小时后，组织者用一组合成凭据把这套绿灯推翻——24 例探针里 6 形完整凭据原样可检索，而上一版 0.4.1 对这 6 形是全遮的。

这不是修 bug 修出的新 bug。是"全绿"本身不可信。

## 一、仪器是产品的镜子

插件自带两把"尺子"：审计脚本 audit-r3 查全库有没有完整凭据可检索；闭包脚本 closure 从源会话提值再回查。它们都是照着产品的打码逻辑写出来的。

第十一轮的实证很直白：产品对"散文里的裸 base62 凭据"没有通用规则（privacy.js 只认 hex、已知前缀、键值句法），于是 audit 对 9 个裸散文形全部 MISS，closure exit 0、leaks=0。产品瞎的地方，尺子一起瞎。三件一起绿，等于三件一起没看见。

所以第一条判据只能是：**扫描器 exit 0 不等于干净，只等于"扫描器没抓到"。**

## 二、负对照：先证明尺子抓得到已知的假秘密

修法不是把尺子做得更严，而是强制它必须抓到注入的假凭据：往库里注入 12 个合成裸形，audit 必须报红（exit≠0）、closure 必须 flag。12/12 RED 才算"尺子能自证"。

之后每一轮新增的攻击形（6 形、13 形、26 形、79 例探针）都要同步扩负对照，缺一不验收。这也是第十四轮最贵的一课：修复批的探针和产品同口径，产品漏它就漏；直到组织者另写一版双谓词对照——0.4.5 和新版各跑一遍，0.4.1 遮、新版留＝新回归——才把六形钉死。

## 三、端到端才是判据

第十轮的教训更狠：closure 对"良性族"开了七条豁免，两例真凭据被端到端放过——64hex 被判成哈希指纹、裸令牌混在 PNG 里被判成图像数据。单元级全绿，端到端漏报。

判据从此升级：**仪器覆盖面 ≥ 泄漏面**。覆盖面窄于泄漏面的绿，一律按"假干净"处理。

## 四、给你自己的检查清单

1. 任何 exit 0 的扫描器，配一组负对照，并让它必须报红；
2. 负对照要放"最丑的形态"：散文裸串、裸表格、编码变形、嵌套、全角；
3. 端到端注入优先于单元测试——真凭据要真的能整段搜出来才算漏；
4. 镜像仪器要双实现或独立 oracle，别让尺子和产品共用一套目光。

## 结尾

"全绿"是一个待证伪的命题，不是结论。这篇讲的不是某插件的八卦，而是一个通用姿势：**当你的检查器和被检查的东西是同一个脑子想出来的，先怀疑那个脑子。** 到第十四轮收口时，这把尺子已经扩到 363 个源凭据值反查全零泄漏——而它最初的样子，是连 9 个裸串都看不见。
