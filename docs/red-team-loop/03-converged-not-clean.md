# 收敛不是清零：带缺口收口的诚实写法

> 系列之三｜素材：dsh-tingfeng2 第十四轮收口

第十四轮的终判叫 CONVERGED，不叫 CLEAN。这个词是硬抠出来的：两个残留没修，但底线的确坐实了。

## 一、底线是哪一条

用户只关心一句话：**我库里现存的完整明文凭据，能不能被检索出来。** 与其修到"理论上不可能漏"，不如把这句话拆成五条独立通道去证：

1. 从 363 个源凭据值反查全库，`close-indep` 结果 363/363 零命中；
2. 独立检查残留 hex 段，命中 0；
3. 审计脚本 `secretLeak=0 / fullRetrievable=0 / realLeak=0`；
4. 全库帧级 diff，真凭据"由掩变留"的候选裁决后为 0；
5. 活库里 35 条带 `$` 的串，全是 `$变量` 形式，无一条高熵真凭据。

五条各自独立、口径不同、互不复用代码。全过，才敢说"活体零泄漏"。这跟"零缺陷"是两件事。

## 二、残留是什么，怎么定性

第十四轮留了两个洞，都是合成探针打出来的，活库里一个实例都没有：

- **P-9 豁免谓词边界族**：`looksLikePlaceholder` 按首字符 `$` 就放行，于是 `$2b$10$…`（bcrypt）、`$+hex32`、`$+base64url43` 这类东西被当成变量放过去；
- **P-10 弱口令回归**：`Pa55w0rd!Strong99` 在 0.4.1 是被无条件遮的，0.4.5 只看高熵、于是放行。这是双谓词一比就现形的回归。

定性必须精确到这一层：**攻击面谓词精度缺口，不是活体泄漏**。两者混淆，要么过度恐慌（继续无限修），要么过度乐观（当成没事）。

## 三、为什么可以停

不是"差不多就行"，是算了账：组件化路线已经把编码、结构、字符集、兜底、保真、性能的常规矩阵跑全，剩下的两个是谓词精度族，在现有路线内可闭合，不需要换解析路线。继续修，每轮要重跑全套仪器、重建 5 万文档的库，一轮四五小时。

于是 22:30 那句"我感觉差不多了，一个小时内收口吧"，把"无限修"换成了"限时收口"。这个决定是对的，但它的前提是前面五条通道已经跑完了——**限时收口只在证据齐了之后才成立**。

## 四、诚实写法长什么样

一段可用的收口声明，应该能让人拿它去复跑：

- 残留清单带编号、带机理、带探针名（P-9/P-10 各自对应哪段代码、哪条探针）；
- 未来风险明确写出来——"若日后活体会话里出现 bcrypt 密码、`$` 起头的高熵 userinfo、path 段凭据，0.4.5 会整段可检索，而 0.4.1 本会遮住"；
- 不写"已全面修复"，写"已有条件收敛，缺口在此"；
- 留一条回头路：源码里 0.4.6 的 partial 状态、修复方向（豁免收窄、rawKv 补兜底、password 位补回弱口令档）都写清楚，将来能接着改。

## 结尾

最贵的不是修不完，是说不清。CONVERGED 带保留，比 CLEAN 难写得多，但它不会在三个月后变成一次翻车。
