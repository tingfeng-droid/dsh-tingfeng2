# 长程不散架：状态文件、离线续跑与断点保护

> 系列之四｜素材：dsh-tingfeng2 反方复验全程（32 小时、14 轮）

十四轮跨了两天，中间还断过一次电（机器离线 5.5 小时）。能续上，靠的不是记性，是三个制度。

## 一、状态文件是唯一源

所有结论只写在一个地方：`循环状态.md`。每轮结束追加一条，格式固定——轮次、终判、判据、残留编号、报告路径、证据目录、台账状态。

好处很具体：换一个执行者（组织者、子代理、主代理），它不需要读历史对话，只读这一个文件就能接手。十四轮里组织者换过、修复子代理被 kill 过、看守定时任务被删过，状态没丢。

反面教训也有：第十四轮一度出现"src/privacy.js 被迭代 5 改到 36297B"这种脏基线，交付必须回到冻结的 tgz。**状态文件要能回答"现在的磁盘状态和交付物是不是一回事"**，所以交付前必做哈希复核。

## 二、离线续跑：让磁盘替你记事

第十二轮跑到一半，机器在 03:26 掉线，09:18 才回来。这 5.5 小时里，修复子代理已经落盘的源码、schema 重建、仪器、负对照全在宿主机磁盘上。回线之后它自己从 `§二` 接着跑，验证 210/53854、`close-r8 3510/3510`、覆盖率全过。

要点只有一条：**把进度做成磁盘上的实物，而不是上下文里的记忆**。脚本、结果 txt、库副本，都落盘。上下文一压缩，记忆就不可靠，文件不会。

## 三、看守：只在没人动的时候叫醒

第十二轮之前挂过两个定时看守，每小时两次检查心跳文件龄：超过 60 分钟就唤醒组织者要求刷新状态，否则 no-op、不插手、不交付。

看守的价值是防"静默停滞"——那种既没报错也没进展的状态。它最关键的纪律是 **no-op 也要留痕**：几点检查、心跳龄多少、为什么判定活跃。后来用户说去掉定时任务，看守删了，但那套判据留了下来。

## 四、成本刹车

第十四轮一轮里塞了四次迭代（0.4.2 → 0.4.3 → 0.4.4 → 0.4.5），每次都要重建五万文档的库、跑全套仪器。这种情况下，"先定上限再开跑"不是客套：一轮迭代、一套仪器、一个交付点，超了就停，把缺口写进状态。

## 五、一个真实的翻车：探针把基线覆盖了

第十三轮 13:40，红队的守卫探针把组织者的共享基线副本 `base13-040.sqlite` 覆盖成了空库。数字当时已经存进归档 txt，离线 diff 不受影响，结论没被推翻——但教训是硬的：**红队探针必须自建临时库，绝不能拿别人的基线当草稿纸**。从那以后每轮派发令里都写死这一条。

## 结尾

长程任务不是靠一次想清楚，是靠每轮收口时把"我现在确信什么、我还没验什么"写下来。状态文件、落盘进度、看守留痕、成本上限，四样凑齐，三十多个小时的项目才散不了架。
